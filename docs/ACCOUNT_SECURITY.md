# 账号访问与两步验证

账号、MFA 和标准 OIDC 接入复用同一个身份边界。Painter 继续使用本地 PostgreSQL 和 Go 单体，不要求额外运行认证数据库、Node 服务或 SaaS。其他项目通过 OIDC 接入；具体协议、数据表与时序见 [认证中台](IDENTITY_PROVIDER.md)。

## 内网阅读与登录地址

生产环境的认证地址由 `PUBLIC_BASE_URL` 决定，例如 `https://blog.example.com/login`。局域网 HTTP 地址可以支持公开阅读；从该地址进入登录或注册时，会先转到配置中的 HTTPS 域名，再显示密码表单，并保留站内返回地址。认证依赖 Secure Cookie，HTTP 局域网的阅读可用不代表登录也可用。

跳转目标只取 `PUBLIC_BASE_URL`，不取访客提供的 Host、转发 Host 或外部返回链接。登录 API 的来源、CSRF 和 Cookie 安全要求保持不变。开发环境使用自己的 HTTP `PUBLIC_BASE_URL` 时仍在本地登录；未来若要求完全不经过公网域名的内部认证，需要独立设计内网 HTTPS 和显式可信来源配置。

登录会验证已有密码，不再套用创建新密码时的最小长度；仍限制 4096 UTF-8 字节以防资源滥用。注册、修改和重置新密码继续执行原来的强度要求。

## 控制注册与登录

站长登录后打开 **站点管理 → 登录安全 → 账号访问**：

- **允许外部账号登录**：控制站长以外的已有账号，包括读者和创作者，以及这些账号关联的应用授权。关闭后撤销其现有登录，并拒绝本地、GitHub 和 OIDC 后续访问。站长仍能登录维护；公开阅读不受影响。
- **允许新账号注册**：控制本地注册和首次使用 GitHub 创建账号。新账号固定为读者。外部登录关闭时，注册也实际暂停；重新开放登录后会遵循所保存的注册开关。

两项均由服务端执行，隐藏界面入口不构成鉴权。设置采用版本校验，遇到其他页面同时修改时需要重新加载，不能覆盖新值。GitHub 开关是额外的提供方配置，不能绕过上述策略，也不会按邮箱或用户名自动合并账号。

## 绑定验证器

1. 打开 **个人中心 → 安全**，找到 **两步验证**。
2. 输入当前密码，选择 **绑定验证器**。只有 GitHub 身份的账号需要先重新通过 GitHub 登录，在 5 分钟内管理绑定。
3. 使用 Apple 密码、1Password 或其他支持 TOTP 的验证器扫描二维码，也可以手动输入密钥。二维码在浏览器本地生成，不向外部二维码网站发送密钥。
4. 输入当前 6 位动态码，选择 **确认并启用**。准备绑定请求 10 分钟内有效；验证通过前不改变登录要求。
5. 将显示的 10 组恢复码保存到私人密码管理器或离线位置。恢复码仅在此次生成时显示，每组只能使用一次；可以主动下载。页面不会将它们写入 localStorage 或应用日志。

启用时旋转当前登录 Cookie 和 CSRF token，撤销其他设备的会话。当前浏览器保持登录；其他设备下次必须完成两步验证。不能用启用之前复制的 Cookie 自动获得第二步认证状态。

## 后续登录与恢复

本地密码或 GitHub 身份验证通过后，若账号已启用 MFA，只建立短期验证请求，不建立完整登录会话。输入验证器动态码，或切换 **使用恢复码**；通过第二步后才可访问后台和批准其他应用授权。

动态码为 SHA-1 / 6 位 / 30 秒 TOTP，允许前后一个时间步的时钟偏差，同一动态码不能重复消费。刚绑定后立即在另一设备登录时，等待验证器下一组码或使用恢复码。登录验证请求最长 5 分钟、最多 5 次尝试，另有持久账号级失败锁定；换 IP、刷新页面或创建新请求不能绕过账号锁定。服务器需要正常同步系统时间。

仍能登录时，可在同一区域重新生成恢复码；旧恢复码立即作废。关闭两步验证需要当前密码（或最近 GitHub 验证）和动态码/恢复码，完成后全部设备退出。

两个验证方式都遗失时，具备本机运维权限的站长可以离线移除指定账号 MFA：

```bash
systemd-run --user --wait --pipe \
  --property="EnvironmentFile=$HOME/.config/painter/runtime.env" \
  "$HOME/.local/share/painter/bin/painter" disable-local-mfa --username admin
```

这是本机数据库运维入口，没有可远程调用的 MFA 重置 API。会写审计并撤销该账号全部会话与未完成验证；随后重新登录并绑定。单独执行 `reset-local-password` **保留 MFA**，避免密码恢复静默降低认证强度。不要将真实密码放进命令参数或 Git；密码 CLI 仍使用标准输入或私有文件。

## 数据与事务

| 数据表 | 内容与保护 |
| --- | --- |
| `local_accounts` | Argon2id 密码散列；从不存储可解密密码 |
| `user_mfa` | AES-256-GCM 加密的当前/准备中 TOTP 密钥，AAD 绑定用户 ID；验证时间步及持久失败窗口 |
| `mfa_recovery_codes` | 域隔离的 HMAC 散列与消费时间；并发原子消费 |
| `mfa_login_challenges` | 独立随机 ID、浏览器令牌哈希、账号版本、认证来源、期限与尝试次数；HttpOnly Cookie 与 CSRF 双重绑定 |
| `sessions` | 登录令牌散列、认证方式、认证时间、MFA 时间、撤销与期限 |
| `site_settings` | 独立注册与外部登录开关；受版本校验及身份策略闸门保护 |

MFA 密钥与 OIDC 签名私钥依赖原部署 `APP_ENCRYPTION_KEY`；备份时必须一同安全保管。[自动备份与恢复](AUTOMATIC_BACKUP_RECOVERY.md) 会保留私有配置快照，并在恢复的新库中废止旧会话、MFA 请求和 OIDC 授权。恢复长期绑定属于时间点恢复：密码和恢复码消费状态也回到该备份时间点，恢复后应重新生成恢复码；不要将旧备份当作无需复核的最新认证状态。

## Cloudflare Tunnel 下的访问限制

默认只按 TCP 直接来源限流，不信任访客提交的 `X-Forwarded-For`。使用 cloudflared 转发时，可显式配置以下示例，并将地址替换为应用实际观察到的代理连接来源：

```dotenv
TRUST_CLOUDFLARE_CONNECTING_IP=true
TRUSTED_PROXY_CIDRS=192.168.1.10/32
```

仅在直接 TCP 来源命中这些可信代理地址后，才使用单个格式正确的 `CF-Connecting-IP`；未知来源、重复值、逗号、端口、IPv6 zone 或异常值回退直接来源。启用时不允许空信任列表或信任全网的 CIDR，完全不读取访客可伪造的 XFF / X-Real-IP。直接对公网开放源站时，应限制谁能到达该受信任入口。规则依据 [Cloudflare 请求头说明](https://developers.cloudflare.com/fundamentals/reference/http-headers/#cf-connecting-ip)，Cloudflare Worker 子请求的地址语义有额外边界。

账号权限、CSRF、验证码持久限流仍由服务端执行，可信 IP 仅改善 Tunnel 下多人共用一个限流桶的问题。WebAuthn/Passkey、邮件验证/自助找回、设备码和组织权限不属于当前已实现能力，后续可在同一认证边界扩展。
