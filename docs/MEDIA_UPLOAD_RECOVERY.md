# 图片上传超时修复

## 现象与证据

2026-11-14 22:06:26（UTC+8），专栏封面上传 `POST /api/v1/media` 收到 Cloudflare 502 HTML。对应 Tunnel 日志为向源站转发上传时 TCP 连接已关闭；同一时间段也有 Tunnel QUIC 重连和网络超时记录，不能据此宣称公网链路没有其它故障。

应用给所有普通 HTTP 请求设置 30 秒读取和写入期限。图片还在上传时，这两项期限也在计时。修复前，在真实 HTTP 服务器上将这项期限缩短到 200ms，并让 multipart 上传跨越 350ms，可稳定复现连接关闭错误。模拟请求体读超时还会误报“无效文件请求”或“上传写入失败”。

## 修复

- 通过登录和 CSRF 校验的图片上传单独设置 5 分钟请求体读取期限，响应写入期限为 5 分 30 秒，给读取结束后的处理和错误响应留出空间。通过 ResponseController 的 Unwrap 协议穿过现有观测中间件，不更改普通接口的全局 30 秒期限或请求头期限。
- 超时返回 JSON 408 / `UPLOAD_TIMEOUT` 和可操作提示；请求体超限仍返回 413。错误路径移除临时图片，不建立成功媒体记录。最大文件大小、像素限制、真实格式校验、CSRF、权限、幂等和持久化协议保持原约束。
- 网关返回非 JSON 的 502／超时类响应时，上传客户端给出重新选择图片重试的提示。仍优先展示服务器已有的结构化错误；不自动重放结果不确定的上传。
- 未改变域名、监听、代理、Tunnel 配置或正式数据库，无新增迁移。

## 验证边界

新增真实 HTTP 回归同时验证：上传跨越普通请求期限仍能完成，而普通接口仍按原期限超时；上传开始前及文件接收中超时均返回明确错误并清理临时文件。现有媒体与专栏回归包含授权、公开可见性、历史引用保护及上传幂等。

独立 PostgreSQL 18 候选使用正式构建方式生成二进制，实际将 multipart 图片分成两段、间隔 31 秒发送，以验证超过原 30 秒限制的上传；随后读取原图片字节、保存到隔离专栏草稿、重新读取并清理夹具。该验证不向正式站点上传图片，也不能代替真实公网或用户原图的验证。

最终检查：显式独立 `PAINTER_TEST_DATABASE_URL` 上全量 `go test ./... -count=1`、媒体定向 race、`go vet ./...`、`make frontend`、Go 程序构建、60 项请求协调检查与 4 项构建混淆检查均通过。31 秒实际上传返回 201，图片字节、专栏封面保存及清理均通过。测试服务和测试 PostgreSQL 结束后停止；正式程序未替换。
